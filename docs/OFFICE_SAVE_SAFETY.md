# 窓口編集：取得失敗と一括保存の保護

2026-11-02。起点main `8a9022e`。ユーザー承認は「DB関数1つと必要な実行権限のみ、テーブル/列変更なし」。[当初調査](OFFICE_SAVE_SAFETY_PROPOSAL.md)の停止判断は承認前の履歴。

## 取得と結果不明時の操作停止

窓口本体（統括組織joinを含む）・管轄地域・市区町村（都道府県joinを含む）・有効な機関種別の取得をすべて検証。error/通信例外/null配列/不正行/重複/選択肢との不整合があればフォームを表示せず、エラーと再読み込みを表示する。窓口本体の正常なnullだけが404。正常な空地域は編集可能、新規の空選択肢も取得失敗と区別し、既存の必須入力検証を維持。市区町村は1000行ずつ取得し、途中ページの失敗も全体を停止する。

送信前に会社情報を含まない窓口フォームの保存意図をsessionStorageへ保持。保存中・結果不明・ページ再読み込み後はフォームを停止する。保存応答のIDと全フォーム内容/管轄地域が一致するまで成功遷移しない。error/通信例外でも処理中を解除し、結果不明の記録は消さない。

「保存結果を確認」は本体・共有組織・地域を再取得し、全保存内容を照合。新規は機関種別/組織名/窓口名の既存一意キーで候補を確認してから全内容を照合する。再取得失敗は停止維持。一致なら一覧へ戻る。不一致/不存在なら保存確認とは扱わず、全取得元を読み直して現在値と新しいbaselineから編集を再開する。無条件再送なし。保存意図が破損/保存先が使えない場合も送信せず、一覧確認の導線を表示。

## DBの変更範囲

`public.save_admin_office(integer,jsonb,jsonb,integer[])` 1つとEXECUTE権限だけ。既存3テーブル・列・制約・RLS・既存関数は変更しない。

- SECURITY INVOKER、空search_path。UID・非匿名・既存admin_usersのメールでDBでも管理者確認。PUBLIC/anon/service_roleのEXECUTEを取消、authenticatedだけに許可し、非管理者は内部でも拒否。
- 統括組織は種別/名前の一致する既存行を無更新で再利用する。存在しなければ新規作成。対象窓口の所属だけを変更し、共有組織の名称・公式URL等や他窓口を更新しない。
- 他窓口が担当する市区町村/機関種別は競合として拒否し、従来のupsertによる暗黙の担当移管を行わない。今回の「対象外の窓口を変更しない」という指定を優先する。
- 組織/窓口/地域を同じトランザクションで保存し、例外時は新規組織を含む全業務行をロールバック。DELETEがRLSで0行となって旧地域が残る場合も失敗。
- 書き込み直前に3テーブルを一定順でSHARE ROW EXCLUSIVEロック。短い管理者の保存同士と旧式の直接書き込みを直列化し、通常の読み取りは止めない。ロック待ち5秒で例外にする。保存頻度の低い管理画面で、スキーマ変更なしに空地域の競合も保護するための選択。表全体の書き込みが短時間待つ点は制約として残る。
- 更新は窓口全列・共有組織全列・管轄地域全行のbaselineを照合。地域だけの直接更新で窓口updated_atが変わらない場合も古い画面の保存を拒否。保存後の返却snapshotも再送判定に使用。

## 検証

- 全598テスト（追加49件）。実SQLをPGlite/PostgreSQL 18.6の使い捨てDBで実行。本番PostgreSQL 17に障害を注入したものではない。
- 正常な新規/編集/空地域、組織再利用/新規作成、他窓口/共有組織の不変、他窓口への割当競合を確認。
- 組織INSERT・窓口INSERT/UPDATE・地域DELETE/INSERTの各段階に例外を入れて3テーブルの全行を比較。権限拒否・RLS DELETE拒否でも全体を維持。PostgreSQLのシーケンス番号は一般仕様として欠番になり得るが、不完全な業務行は残らない。
- 匿名/匿名サインイン/一般ユーザー/UIDなし/service_roleを拒否。同じbaselineの重なる2送信は1件だけ成功し、窓口/共有組織/地域だけの変更後にも古いbaselineを拒否。PGliteは単一バックエンドであり、複数接続のロック待ち時間の実測ではない。
- `npm run test:e2e:office-save-safety`: 認証以外は全て合成データ。取得4元のerror/例外/不正行、副取得null、正常な空地域、新規選択肢失敗、正常単一RPC保存、error/通信例外/保存後応答喪失、再読み込み後の再送停止、再取得失敗で停止維持、新規重複送信なしを確認。実DB書き込み0件。
- Lint/通常本番ビルド/型チェックとPR/main CIの確定結果はPRに記録。本番は新規/編集の画面読み取り、関数定義と権限、デプロイだけ確認し、実運用の組織/窓口の試験保存は行わない。

## 限定適用

1. 最新main/オープンPRとマイグレーション内容をレビューする。`supabase/migrations/20261102113709_save_admin_office_atomic.sql` のSHA-256を記録。
2. 本番の既存3テーブルの全行ハッシュ、列/制約/RLS、対象関数の不存在/既存定義、security advisorsを読み取り記録。既に関数がある場合は同一定義か確認し、重複適用しない。
3. PR CI成功後、Supabaseのapply_migrationでこのSQLファイルの内容だけを適用する。他のSQLファイルは実行しない。適用APIの履歴時刻とファイル時刻が異なる場合も、定義ハッシュを照合して重複適用しない。
4. 関数のinvoker/search_path/lock_timeout/ACLと本文を確認。対象3テーブルの全行・定義のハッシュを比較し、意図しない変更があれば止めて調査する。新関数は既存アプリには呼ばれないため、アプリ公開より先に配置できる。
5. 対応アプリをマージしmain CI・本番READY・独自ドメインの新コード配信を確認。窓口新規/既存編集を読み取り確認。全ブラウザ書き込みを遮断し、実運用窓口の保存/削除や本番障害試験をしない。

## 復旧

`supabase/rollback/save_admin_office_atomic.sql` は今回の関数のEXECUTE取消と削除だけ。テーブル/列/データ/既存関数は変更しない。復旧SQL自体もローカルDBで確認済み。

アプリは今回の安全な単一RPC版を維持する。関数がなくなると保存は失敗し、結果不明の記録と再取得の導線を保持する。旧版の個別DELETE/upsert保存へロールバックしない。保存再開は、レビュー/検証した今回の関数だけを再適用し、再取得で既存の保存結果を確認してから行う。履歴件数やファイル名だけを根拠に過去SQLを一括適用しない。
