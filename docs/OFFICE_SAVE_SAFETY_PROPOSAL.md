アプリ実装・DB定義変更・PR・CI・マージ・デプロイは未実施。実運用窓口の保存・変更・削除は行っていない。本番DBは関数/列/制約/RLSのメタデータを読み取り確認しただけ。

## 未修正の取得経路

- 編集ページ `src/app/admin/(protected)/offices/[id]/page.tsx` は窓口本体（統括組織joinを含む）・管轄地域・市区町村（都道府県joinを含む）・有効な機関種別を並列取得するがerrorを確認しない。
- 管轄地域/市区町村/機関種別のnullを空配列へ変換。窓口本体の取得失敗は正常な不存在と同じ404となる。統括組織join欠落は空の名前/種別になる。
- 新規ページも選択肢の取得失敗を空配列化する。選択肢取得の通信例外には再読み込み付きの専用エラー表示がない。

現行 `OfficeForm.tsx` の実際の `handleSubmit` をTypeScript ASTで抽出し、全DB呼び出しをローカルの合成データへ差し替えた。正常1件・異常等7件の8シナリオでassertion成功。これは現状の不具合の再現であり、修正の検証ではない。実DB書き込み0件。

## 変更案

### アプリの取得保護

編集専用loaderで4取得元すべてとjoinを検証。error/例外/null配列/不正行/取得内容の不整合ならフォームを渡さず、エラーと再読み込みを表示する。窓口本体が正常なnullのときだけ404。正常な管轄地域0行は編集可能。正常な空選択肢も取得失敗とは区別し、既存の必須項目の検証を維持する。既存の選択値が候補に存在しない場合は、空へ置き換えて保存しない。新規ページも選択肢の取得不可では編集/保存停止。

### 一括保存関数1つ（要承認）

仮称 `public.save_admin_office`。入力は窓口ID（新規null）、読み込み時の窓口更新時刻と組織/地域のスナップショット、フォーム本体、選択市区町村ID。戻り値は保存ID・更新時刻・確認用の保存内容。

1. SECURITY INVOKER、固定search_path、既存RLSを維持。関数内でもauth.uid・非匿名・admin_usersによる管理者確認。PUBLIC/anon/service_roleのEXECUTEを取り消しauthenticatedにだけ許可、非管理者は関数内で拒否。テーブルRLSの緩和やservice_roleキー追加なし。
2. 既存窓口をロックし、更新時刻だけでなく組織と地域の読み込み時スナップショットも照合。地域だけの変更は窓口updated_atに反映されない可能性があるため、時刻だけに依存しない。
3. 同一トランザクション内で組織の再利用/新規作成、窓口保存、地域置換を実行。DELETEの影響行も検証し、RLSの0行を成功扱いしない。途中例外は組織を含む全体をロールバック。
4. 管轄地域の一意キーは `(municipality_id, organization_type_id)`。他窓口からの担当移管も現行どおり行う場合は、対象となる既存担当行と競合窓口を事前読取/確認の対象に含め、スナップショット照合・一定順のロック・結果確認を同一トランザクションに含める。予期しない担当変更は競合として拒否し、盲目的なupsertにしない。既存の担当移管仕様そのものを無断で廃止/拡張しない。
5. 一意制約/FKと競合検査を維持し、並行新規作成/空地域への同時割当も片方が競合失敗になるよう検証。テーブル/列追加・変更は不要の想定。

関数だけを対象とする限定マイグレーションと取消/削除の復旧SQLを用意し、既存SQLの一括適用はしない。復旧時は旧式の個別書き込みへ戻さず安全なアプリで保存停止。今回の関数だけ再適用して再開。

### 保存中・結果不明

単一RPCへ置き換え、保存中は編集と多重送信を停止、finallyで処理中解除。送信前にセッション記録を確保し、応答喪失時は再読み込み後も保存を止める。組織/窓口/地域と、移管がある場合の影響先も再取得して一致を確認するまで成功表示や無条件再送を行わない。新規作成も既存の組織種別/組織名・窓口名の一意キーと全内容照合で結果を確認し、同名だが別内容を成功扱いしない。

## 承認後の検証と反映

- 4取得元とjoinそれぞれのerror/例外/null/不正行、正常な空地域・空選択肢、再読み込み後の復帰。
- ローカル合成画面で取得失敗の編集停止と再取得、保存中/結果不明の再送停止、正常保存と新規の応答喪失後の確認。
- 使い捨てPostgreSQLで組織作成/窓口保存/地域DELETE/各登録の全段階に障害を注入し、全体が元へ戻ることを確認。担当移管とその失敗も別窓口まで含めて検証。管理者/匿名/一般ユーザー、競合更新も試験。
- PR・CI後、関数だけ限定適用して対応アプリをマージ/本番反映。本番は新規/編集画面と関数定義/権限の読み取りだけ。実運用窓口の試験保存・障害注入は行わず、本番正常保存を試験済みとは報告しない。

公式仕様: [PostgRESTのリクエスト単位のトランザクション](https://docs.postgrest.org/en/stable/references/transactions.html)、[Supabase Database functions](https://supabase.com/docs/guides/database/functions)。個別REST要求の補償書き戻しは、補償自身の通信失敗/競合があり全体復元を保証しない。
