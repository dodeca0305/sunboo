# 入力・編集画面の取得失敗点検（2026-10-31）

## 範囲・判定基準

最新main `d3189e7`（PR #141反映済み）を起点に、主要画面の取得→初期値変換→保存先までをコードで追跡した。取得error・nullと正常な未登録が混同され、既存キーへの更新/upsertへ到達するかを確認。本番の既存データを上書きする再現は行っていない。

| 年間ロードマップ | 納税予定の取得失敗と正常な0件を区別し、失敗時の予定税額入力・保存を停止（2026-11-02追記）。手続き状態の取得失敗を空Mapへ変換する経路は残る | 納税予定を修正。手続き状態は未修正 |

## 今回の選定理由

会社プロフィールは1回の保存で複数の税務・労務・住所項目をまとめて上書きでき、以後の手続き判定の前提にもなる。利用者の会社別データを直接保護でき、架空会社だけで検証可能なため、今回の1件として優先した。その他の課題を解決済みとは扱わない。

## 修正

- 編集専用 `loadWorkspaceProfileForEditing` を追加。プロフィール・都道府県・市区町村いずれかの取得error/通信例外/不正レスポンスを編集不可として返す。
- プロフィールが正常なnull（まだ行が無い）の場合だけ既定値を使い、新規入力を維持。
- 読み込み失敗時はエラーと再読み込みリンクを表示。フォーム自体を渡さず、空欄・0の保存を防ぐ。
- 正常な既存プロフィールの全項目・保存payloadの変換を維持。DBスキーマ・権限・保存処理は変更しない。
- 共用loaderの読み取り画面への影響を避けるため、変更はプロフィール編集ページの取得処理に限定。

## 2026-11-02: 書類・必要書類の取得失敗対策

### 選定と範囲

PR #143反映済みmain `6c619b8` を起点に、オープンPRなし・旧作業の保護を確認して着手。書類の登録済み・必要書類の準備済みが取得失敗で未登録/未準備に見え、その状態から既存行を更新できるため優先した。書類編集画面とその保存を保護し、納税予定保護の再実装はしない。

### 実装

- 編集専用loaderで `workspace_documents` / `workspace_required_document_statuses` を会社IDで絞り込んで並列取得。片方でもerror・例外・null/不正応答・不正行があれば全体を取得不可とし、正常な0行だけを未登録として扱う。
- 取得不可の場合は登録件数を0と表示せず、エラー・再読み込みを表示して状態変更フォームを渡さない。ロードマップ組み立ての例外も空の必要書類一覧へ変換しない。
- 保存成功後だけ表示を更新。保存中は両方の状態変更を止め、同一描画中の連打も抑止。error/例外・結果不明時は処理中表示を解除し、再取得まで再送を止める。
- 共用の読取loader、ホームの集計/通知、ロードマップ手続き状態の取得失敗、ルール/窓口の編集、決算実績は別の残課題として維持。DBスキーマ・RLS・既存SQLの適用は変更なし。
