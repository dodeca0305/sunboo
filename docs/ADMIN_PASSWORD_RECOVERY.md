# 管理者のパスワード再設定

初期版の通し試用/DB限定適用/本番反映後、利用者がパスワード不明と回答したため、既存Supabase Authに再設定の入口を追加する。管理者/メンバーの権限付与や変更、DBの追加変更、パスワードの強制設定、ログインの迂回はしない。

## 本人の操作

1. ChromeのSUNBOOプロフィールで `/admin/forgot-password` を開き、登録メールアドレスへ再設定リンクを依頼する。
2. メールのリンクを、依頼した同じブラウザ/プロフィールで開く。PKCEの確認に送信時のブラウザ保存領域が必要。
3. `/admin/reset-password` に対象アカウントが表示されたことを確認し、本人が12文字以上の新しいパスワードと確認欄を入力して確定する。
4. 変更の確認後、ログイン画面から新しいパスワードでログインする。

パスワードの入力/確定、メールの実送信/本人リンクの操作はエージェントが代行していない。2026-11-04に本人が再設定完了と回答し、その後の管理画面ログイン成功を確認した。メールの戻り先として `https://www.sunboo-keiei.com/admin/reset-password` がSupabase Authで許可されている必要がある。2026-11-04に本人の承認を受け、Site URLをhttps://www.sunboo-keiei.comへ変更し、上記の完全一致URLだけを許可リストへ追加、再読込で保存を確認した。リンクが別URLへ戻る場合は設定確認が必要で、ユーザー/権限を作り直して迂回しない。

## 実装境界と検証

- 再設定メールは既存 `resetPasswordForEmail` を使用。登録の有無を画面へ露出させず、結果不明時に自動再送しない。
- ブラウザSDKのPKCE交換/`PASSWORD_RECOVERY`とサーバーによる本人確認が揃った場合だけ新しいパスワードの入力を表示する。無効/期限切れ/異なるブラウザでは停止する。通常セッションだけで初回の再設定フォームは出さない。
- 新しいパスワードは保存領域/ログ/計測に記録しない。保存領域には本人IDと非秘密の状態だけを保存する。送信前に結果不明の印を保持し、通信例外や5xxでは再読み込み後も無条件再送しない。
- 変更は本人のAuth APIへ送り、現在の利用者と返却された利用者を照合する。確認できた場合だけ成功と表示する。会社の設定/税務実行/業務データには触れない。
- 公開する管理用パスはログイン/再設定依頼/再設定の完全一致3個だけ。保護画面の認証/管理者確認は維持する。
- 再設定ページではアクセス解析スクリプトを読み込まず、Referrer Policyをno-referrerにし、SDKの確認後にURLのコード/フラグメントを取り除く。
- ローカルの合成Auth応答で、実SDKのPKCE→本人確認→変更、無効セッション、確認欄不一致、通信応答喪失/再読み込み後の停止、保護ページへの移動、計測停止を検証済み。実メール送信/実パスワード変更/本番障害試験はなし。

追加後の全898テスト・型チェック・通常ビルドが成功。Lintは既存警告1件のみ。実メール/パスワードの本人操作前に、合成SDKの再設定画面と保護を確認した。


## 実メール運用で確認した制限（2026-11-04）

認証ログにbad_code_verifier、短時間再送拒否、プロジェクトのメール送信上限(429 over_email_send_rate_limit)を確認した。ローカル合成SDKでは、送信成功後の再送が429で拒否されると、先行メールの確認キーが保持されないことを再現した。実メールを試験目的で追加送信していない。

メール依頼は1回にし、再送せず、同じChromeプロフィールで最新メールのリンクを1回開く。上限時に迷惑メール到着待ちや連打で解決しようとせず、時間を空ける。解除の正確な時刻は未確認。この時点では一般的なエラー表示で、429専用案内と再読込/複数タブ間の再送抑止は未実装だった。後続の再送保護でアプリ側を対応した（以下）。独自メール配信の設定や費用が必要なら別途提案する。最終の本人ログイン後、架空会社23の7画面を読み取り確認し、業務データ/DB定義/権限の前後確認値が一致した。


## 再送保護の追加（2026-11-04）

認証サービスの送信上限とアプリの確認キー破損を分けて扱う。サービスの上限・Auth設定・権限・課金は変更しない。

- 送信専用の非singleton SDKクライアントにCookieアダプターを渡し、確認キーの生成/削除をメモリー内で保留する。明確な4xx拒否では実Cookieへ一切反映せず、先行メールのキーを保持する。成功または通信結果不明では生成したキーだけを反映する。SDKがcatch内でキーを削除しても、結果不明時には生成済みキーを保持する。セッションCookieの変更はこのアダプターから反映しない。保存中に確認キーの別変更を検出したら上書きせず結果不明とする。パスワードやキーのバックアップをlocalStorage/ログへ追加しない。
- ネットワーク前に依頼ID・日時・状態・次回確認時刻だけをlocalStorageへ記録する。Web Locksで同じoriginの複数タブを排他し、ロック取得後にも依頼記録を再確認する。再読込・タブ終了・途中中断のsending状態は自動再送しない。別アカウントのメールアドレスへ変えても同じブラウザーの未確定依頼を無条件に上書きしない。
- 成功/結果不明/一般拒否は最低60秒、429は保守的に1時間、再依頼の確認を待つ。これはアプリの待機目安で、Supabaseの上限解除時刻を推定したものではない。時間後も最新メール確認と「以前のメールが使えなくなる可能性」の明示確認、本人の送信ボタン操作が必要。自動タイマー送信なし。
- 保存領域の利用不可・破損・記録不成立、Web Locks未対応では送信を停止。パスワード変更成功の本人ID照合後に、その画面が確認した依頼IDだけを消す。別タブの新しい依頼は消さない。パスワード変更の結果不明/再読込保護は従来どおり。
- 既存版で送信済みのメールには新しい依頼記録がない。先のメールをまず確認し、不要な再依頼を避ける。新しい明確な拒否では既存版のCookieも保持する。Cookie消去・別ブラウザー/プロフィール・別origin/別端末は保護の共有対象外。保存領域を消して再送し直さない。

ローカル合成試験: 実SDKの送信→429拒否→先行コードのPKCE challenge照合→本人確認→変更、同時2タブ1送信、再読込/他タブ/途中中断の再送停止、応答喪失後の生成キーによるPKCE復旧、保存領域/ロック不可の送信停止が成功。既存の確認欄不一致・無効リンク・変更応答喪失/再読込・保護ルート・再設定ページの解析停止も回帰成功。実メール送信・実パスワード更新・業務書き込みは0件。

復旧時は今回のアプリ変更を戻すPRで扱う。DB/権限/送信上限の変更や既存SQL適用は不要。元へ戻すと再送保護を失うため、利用者へメール依頼を1回に限定する運用を案内する。新しい非秘密の依頼記録を本番で試験目的に消去しない。
