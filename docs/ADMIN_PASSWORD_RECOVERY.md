# 管理者のパスワード再設定

初期版の通し試用/DB限定適用/本番反映後、利用者がパスワード不明と回答したため、既存Supabase Authに再設定の入口を追加する。管理者/メンバーの権限付与や変更、DBの追加変更、パスワードの強制設定、ログインの迂回はしない。

## 本人の操作

1. ChromeのSUNBOOプロフィールで `/admin/forgot-password` を開き、登録メールアドレスへ再設定リンクを依頼する。
2. メールのリンクを、依頼した同じブラウザ/プロフィールで開く。PKCEの確認に送信時のブラウザ保存領域が必要。
3. `/admin/reset-password` に対象アカウントが表示されたことを確認し、本人が12文字以上の新しいパスワードと確認欄を入力して確定する。
4. 変更の確認後、ログイン画面から新しいパスワードでログインする。

パスワードの入力/確定、メールの実送信/本人リンクの操作はエージェントが代行していない。実際のメール配送と本人による完了は未確認。メールの戻り先として `https://www.sunboo-keiei.com/admin/reset-password` がSupabase Authで許可されている必要がある。URL設定は変更しておらず、管理画面への本人ログインが必要なため許可リストの読み取り確認も未完了。リンクが別URLへ戻る場合は設定確認が必要で、ユーザー/権限を作り直して迂回しない。

## 実装境界と検証

- 再設定メールは既存 `resetPasswordForEmail` を使用。登録の有無を画面へ露出させず、結果不明時に自動再送しない。
- ブラウザSDKのPKCE交換/`PASSWORD_RECOVERY`とサーバーによる本人確認が揃った場合だけ新しいパスワードの入力を表示する。無効/期限切れ/異なるブラウザでは停止する。通常セッションだけで初回の再設定フォームは出さない。
- 新しいパスワードは保存領域/ログ/計測に記録しない。保存領域には本人IDと非秘密の状態だけを保存する。送信前に結果不明の印を保持し、通信例外や5xxでは再読み込み後も無条件再送しない。
- 変更は本人のAuth APIへ送り、現在の利用者と返却された利用者を照合する。確認できた場合だけ成功と表示する。会社の設定/税務実行/業務データには触れない。
- 公開する管理用パスはログイン/再設定依頼/再設定の完全一致3個だけ。保護画面の認証/管理者確認は維持する。
- 再設定ページではアクセス解析スクリプトを読み込まず、Referrer Policyをno-referrerにし、SDKの確認後にURLのコード/フラグメントを取り除く。
- ローカルの合成Auth応答で、実SDKのPKCE→本人確認→変更、無効セッション、確認欄不一致、通信応答喪失/再読み込み後の停止、保護ページへの移動、計測停止を検証済み。実メール送信/実パスワード変更/本番障害試験はなし。

追加後の全898テスト・型チェック・通常ビルドが成功。Lintは既存警告1件のみ。実メール/パスワードの本人操作前に、合成SDKの再設定画面と保護を確認した。
