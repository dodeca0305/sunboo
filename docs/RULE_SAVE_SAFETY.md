# 管理用ルールの取得・一括保存保護

2026-11-02。起点main `65ba855`。ユーザーが一括保存用DB関数1つの追加を承認。テーブル・列の変更は対象外。

## 実装と安全性

- 編集ページは本体・条件・実行内容・手続き候補の4取得元を確認。error/例外/不正応答が1つでもあればフォームを渡さずエラーと再読み込みを表示。正常な本体nullは404、条件/実行内容の正常な空配列は編集可能。新規ページも手続き候補の取得失敗時は保存不可。
- `save_admin_rule` の1 RPCで基本情報・条件・実行内容を保存。親行をロックし、既存のupdated_atで同時編集を検出。途中の例外は握りつぶさず全体をロールバックする。新規作成も不完全な親/子を残さない。
- SECURITY INVOKER、空のsearch_path、既存RLSを維持。DB側でauth.uid、匿名サインインではないこと、admin_usersへの登録を検証。PUBLIC・anon・service_roleのEXECUTEを取り消し、authenticatedにだけ許可（DB所有者を除く）。一般の認証ユーザーも関数内で拒否。
- RLSでDELETEが0件になった場合も旧設定が残っていれば例外にし、旧/新設定の混在を成功扱いにしない。
- 保存中はフォームを停止しfinallyで処理中表示を解除。結果不明の要求はsessionStorageに保持し、ページを再読み込みしても再送しない。「保存結果を確認」で全設定を再取得し、送信内容との一致/元の設定の維持/別の更新/取得不能を区別する。
- 新規は既存の名称一意制約と名称による再取得を使う。不存在を確認後に再保存する場合も、最初の要求が遅れて成功していれば一意制約で二重作成を拒否する。自動再送はしない。
- 保存の入力条件（実行内容1件以上等）は維持する。正常な空設定は画面の編集を許可するが、従来の保存バリデーションを外すものではない。

## 検証

- 単体試験: 4取得元の失敗/例外/null/不正応答、正常な空設定、保存結果の一致/未反映/競合/再取得失敗、新規の名称検索。
- PostgreSQL試験: `tests/adminRuleTransaction.test.mjs` はPGlite（PostgreSQL 18.6/WASM、使い捨て）で実際のPL/pgSQL・RLS・GRANT・トランザクションを実行。本番PostgreSQL 17系そのものや本番保存の試験ではない。
- 既存/新規の親更新/作成・条件DELETE・実行内容DELETE・条件INSERT・実行内容INSERT直後の障害で、3テーブルの行が元に戻ることを確認。実際のFKエラー、RLSでDELETE不可、管理者の正常保存・空条件・複数実行内容、名称重複・更新時刻競合、匿名/一般ユーザー/UIDなし/匿名サインイン拒否、関数だけの復旧SQLも確認。
- `npm run test:e2e:rule-save-safety`: 認証以外のDB通信を合成し、実DB書き込みを遮断。取得失敗の操作停止と正常な空設定、単一RPC保存、未反映/保存済み応答喪失、新規応答喪失、確認中の再取得失敗、ページ再読み込み後の保護を確認。
- ローカルの通常ビルドは既存のTurbopack日本語フォント解決で失敗。Webpack本番ビルド・型チェックは成功。通常ビルドはPR/main CIでも確認する。
- 本番の実運用ルールへの保存・変更・削除・障害注入はしない。DB定義/権限・拒否応答・正常な画面読み取り・新コード配信のみ確認し、本番の正常保存を試験済みとは扱わない。

## 復旧手順

関数に問題がある場合は、先にルール保存の利用を止める。安全な新アプリを維持し、旧版の個別UPDATE/DELETE/INSERTへ戻さない。

- 緊急停止SQL: `supabase/rollback/save_admin_rule_atomic.sql`。今回の関数のEXECUTEを取り消し、同じシグネチャの関数だけをDROPする。CASCADEは使わず、他の依存がある場合は停止して確認する。テーブル/ルール行は変更しない。
- 新アプリはRPC不在/拒否を保存結果不明として扱い、直接の削除/再登録へフォールバックしない。保存中だった要求は再取得して確認し、再送しない。
- 再開時は関数が存在しないことを確認し、修正・再検証した今回の関数だけを限定適用する。復旧適用を記録し、権限・拒否応答・定義ハッシュ・データ不変を再確認する。履歴が存在することを理由にSQLを一括再実行しない。
- 関数は1リクエストのトランザクションなので、失敗要求に対する運用ルールの手動再投入は行わない。応答喪失時は登録内容を読み取り、成功/未反映/別更新を区別する。
- マイグレーションはコード公開前に加えるため、アプリをまだ公開していない時点なら関数だけの取り消しが可能。旧アプリの保存経路の危険性は解消していないため、それを安全な復旧手段とは扱わない。
