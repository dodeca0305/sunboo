# 初期版：プロフィール保存関数の追加承認案

2026-11-03。先に承認された会社登録用台帳1つ/関数1つ/4ポリシー変更はその範囲で進める。本追加分は未承認・未適用。

## 新たに確認した必須問題

既存のプロフィール保存は `workspace_companies` の法人形態/決算月UPDATEの後、別要求で `workspace_company_profiles` をupsertする。実handleSubmitを抽出したローカル合成試験で、会社の決算月が3月→6月へ確定した後にプロフィール保存を拒否すると、従業員数は旧7人のまま残る部分保存を再現した。UIは成功を出さないが、次回の案内が新旧混在の入力になる。前回までの取得失敗保護は、この2要求の原子性を保証していない。

## 追加する最小範囲

**新しいDB関数1つ**（仮称 `save_workspace_company_profile`）と、そのauthenticated実行権限だけを追加する。テーブル/列追加・既存RLS/GRANT変更は追加しない。会社登録の台帳を他用途へ流用しない。

- `p_company_id`・初期読取の会社/プロフィールの完全な更新対象値（未登録はnull）・保存したい会社/プロフィール値を受け取る。
- SECURITY INVOKER、固定search_path。uid/非匿名/管理者/当該会社ownerまたはmemberをDBでも確認し、既存RLSを維持する。匿名/閲覧者/他社を拒否。
- 会社行をロックして直列化する。現在の会社/プロフィール値が期待値と異なれば競合として拒否し、古い画面から上書きしない。
- 会社とプロフィールを同一transactionで保存し、どちらの段階でも失敗すれば全変更を取り消す。既存表の列定義/税務基準/期限計算は変えない。
- 現在値が既に要求値と完全一致していれば書込せず保存済みを返す。プロフィールはcompany_id主キーの1行なので、同じ要求の再送で新規行を増やさない。
- 保存結果不明時は送信前の入力を保持し、会社/プロフィールを再取得して一致を確認するまで成功表示や新規保存をしない。確認後の明示的な再試行も期待値を固定し、遅れた要求や同時編集をCASで拒否する。
- 復旧はこの関数だけの安全停止と新画面の保存停止。危険な2要求保存に自動で戻さない。既存データは削除/一括書換しない。

## 検証・本番制約

ローカル合成DBで正常/正常未登録/各段階失敗/全体ロールバック/同時編集拒否/同じ値の再送/応答喪失後の再取得/権限拒否を検証し、通し試用にも含める。本番は定義/ACLの限定適用と架空会社23の読み取りだけで、プロフィール保存試験はしない。追加概算は3〜5時間（初回見積の合計は19〜31時間へ更新）。
