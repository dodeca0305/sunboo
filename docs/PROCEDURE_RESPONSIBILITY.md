# 担当の選択・保存（2026-11-07）

## 承認と対象

利用者がBusiness側の「SUNBOO_担当選択_DB変更案.md」を承認。既存workspace_procedure_statusesに任意のresponsible_role列1つと値チェック1つだけを追加する。新しいDB関数・テーブル・権限/RLS・トリガー・課金・共有RPCの変更はしない。

基点main 363aa6f / PR #176。ログイン済みの会社管理ロードマップで、担当欄を既存の矢印付きプルダウンへ変更する。選択肢は自社の事務担当/顧問税理士/委託事業者/その他の担当/まだ決めていない。未選択NULLと明示的なundecided、取得不可は区別する。選ぶだけで保存し、依頼送信やアクセス権の付与にはしない。

担当は会社・手続き・期限単位。匿名の共有画面へ担当の値を追加公開せず、従来の役割の目安を表示する。共有の「未設定」という表示は実際の担当を表すものではないため、役割の目安という表現にする。税務判定・期限・金額・対応状況の保存値は変更しない。

## 保存の保護

- 会社が取得できることも確認し、権限喪失による0行を正常な未登録と誤認しない。担当または対応状況を取得できない間は担当変更を停止する。
- 既存行は会社/手続き/期限/更新時刻を条件に担当列だけを更新。正常な未登録だけINSERTし、同時INSERTの競合を上書き/自動再送しない。新規行の対応状況は既存の既定値not_started。既存の対応状況は担当保存で上書きしない。
- 選択時に最新データを読み直し、画面の版が古ければ更新内容を表示して選び直す。保存の返却値と再取得を確認するまで成功と表示しない。
- 書込みより前に会社別の未確認操作をlocalStorageへ記録し、Web Locksで同じ会社の多重送信を防ぐ。通信結果不明は再読み込み後も再送せず、明示的な「担当の保存結果を確認」で読むだけ。
- 保存済みの新しい担当を、遅れて届いた古いサーバー再取得で戻さない。更新時刻のマイクロ秒も比較する。通常の担当操作で行の削除は行わない。
- ブラウザ保存領域/排他制御が使えない場合は安全に保存できない旨を表示し、未確認の書込みを継続しない。

## 既存保存との両立

既存の対応状況upsertの送信列は会社/手続き/期限/statusだけ。PostgRESTはその列集合だけを競合時更新するため、今回の担当列をNULLで上書きしない。クライアント要求の列と、同じ列集合のSQLによる相互保持をローカルで検証する。担当保存のUPDATEもresponsible_roleだけ。

一次資料：[PostgRESTのupsert](https://docs.postgrest.org/en/stable/references/api/tables_views.html#upsert)、[SQL生成の列集合](https://github.com/PostgREST/postgrest/blob/v14.1/src/PostgREST/Query/QueryBuilder.hs#L112)。Supabaseの現行変更履歴を確認し、CLI v3はローカル専用のmigration newだけを使用。既存SQLの一括適用やdb pushはしない。

## 限定マイグレーション

公式CLIが作成したsupabase/migrations/20261107120608_add_procedure_responsible_role.sqlだけを適用する。nullable列とCHECKの追加を1トランザクションで実行し、ロック待ちは5秒、処理は30秒で打切り。既存行を推測で埋めない。既存のPK・updated_atトリガー・4ポリシー・GRANTを維持する。

適用前に列/制約/権限/ポリシー/トリガー/共有関数を保存。新列や同名制約が既にある場合は適用を止めて照合する。対象表を参照する公開関数はget_shared_workspace_viewのみで、返すstatus項目はprocedure_id/occurrence_key/statusの明示列。参照ビューはないことを適用前に確認した。

## 検証

全995テスト成功。合成UIで未登録・既存値・明示未定・複数期限、担当/対応状況の相互保持、古いタブの上書き拒否、保存後応答喪失と再読み込み、拒否/再取得失敗と回復、取得error/例外/null、無条件再送なし、矢印と375pxを確認する。ホーム・金額の空欄/明示0/保存保護・電子申告入口・共有/出力の回帰も含む。すべてローカルの合成認証/合成データで行う。

ローカルPostgres互換DBでは、承認したマイグレーション、既存行不変、CHECK拒否、トランザクション全取消、更新時刻CASと競合INSERT、RLSによる別会社/閲覧者/非管理者メンバー/匿名の拒否、共有RPCが担当列を公開しないことを検証する。

本番は今回の限定DDLと架空会社23の読取りだけ。担当を実際に選んで保存したり、実税務実行/共有発行を試験しない。PR/CI/限定適用/マージ/配信と前後照合の最終値はBusiness側記録へ残す。

## 復旧・残課題

アプリを前配信へ戻して担当操作を止める。担当列と保存した値は削除せず保持する。完全な列削除は、保存済みデータの保護方法を確認して別途承認を得る。復旧のための新しいDB関数/権限変更は不要。

承認前の構造/ポリシー/共有関数、移行前後のハッシュ、アドバイザー結果はBusiness側backups/2026-11-07-procedure-responsibility/へ保管。変更前からの共有関数/updated_at関数や既存RLS性能の警告を、今回の担当追加で新設された問題と混同しない。今回の範囲外を自動修正しない。参考：[関数search_path](https://supabase.com/docs/guides/database/database-linter?lint=0011_function_search_path_mutable)、[RLS初期化計画](https://supabase.com/docs/guides/database/database-linter?lint=0003_auth_rls_initplan)。

顧客アカウントの新規権限付与、匿名共有の編集権、個人への依頼送信、将来分の自動担当割当は対象外。選択のしやすさは利用者の再試用で確認する。必要書類の案内不足と、全体を短い説明＋選択中心にしたい希望は別の残課題。横断分析/書類整理連携は次期計画のまま。
